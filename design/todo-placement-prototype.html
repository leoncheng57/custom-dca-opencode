Where it lives

Desktop ≥1024px: a fixed w-80 (320px) right aside, first of five inspector tabs and the default selection. Below lg: a modal sheet behind an icon, so it is zero-glance — invisible until deliberately opened.

The progress affordance today

A native <progress> at h-1.5 full-width, plus the text {completed}/{total} done, plus a count on the tab label. All three live inside the panel, so none of them is visible while the panel is closed or another tab is selected.

The gap this proposal addresses

Progress exists but is co-located with the thing it describes. On mobile the list is behind a tap; on desktop it is behind a tab. A reader watching the transcript has no ambient signal that the plan moved.

Why it “sometimes doesn't update”

Almost never a permission problem. Either the agent simply did not call todowrite this turn, or you are inside the ≤3s poll window. Refresh is pull-based, so latency is bounded by the timer, not by the event.

Constraint every placement inherits

Todo has no id (AGENTS.md). Rows are keyed by index + content, so a reordered list is indistinguishable from an edited one. Any animated ring must tolerate the whole array being swapped, and must not imply per-item identity it cannot prove.

3  Why Plan is allowed to write todos

Not an upstream quirk and not an oversight — a deliberate line in this repository's BFF.

Plan mode does not enumerate what it permits. It asks OpenCode for the live tool catalogue, subtracts a constant allowlist, and appends deny for everything that remains (server/opencode/sessions.ts:519–522). todowrite is a member of that allowlist (:32–42), so it is never in the deny set — there is no rule to strip it.

The rationale is sound

A todo list is a plan artifact, not a mutation of the user's workspace. Denying todowrite would leave Plan mode able to reason about work but unable to record it — the one thing the mode exists to do. Writes stay blocked; the notebook stays open.

Design consequence

A todo ring will move during Plan turns, when no file has changed. Any placement that reads as build progress will lie. Wherever it lands it must be legible as plan progress, and should sit near the existing mode pill rather than near diff or file affordances.

Two rules the ring must not break

Never render failure as zero. Todos are fetched with Promise.allSettled and may fail while everything else succeeds; an empty green ring would silently claim “nothing to do”. The dashed ? state is mandatory, not decorative.

Never animate per item. With no id, a replaced array cannot be diffed into “item 3 completed”. Animate the aggregate arc between two totals and nothing else.

7  Recommendation

Ship #2, keep the panel where it is

The complaint is not that the list is in the wrong place — a 320px panel is the right home for four wrapping rows with two badges each. The complaint is that progress is only visible from inside that panel. Alternative 2 adds an always-visible ring next to the mode pill and leaves TodoPanel untouched: no layout cost, no new fetch, and the adjacency states plainly that this is plan progress, which §3 shows is exactly what it is.

Then #10, and only then reconsider #7

The Hub ring is the next real gain — triage before opening a session — but it inherits the Recents fan-out cost and must render the dashed ? rather than an empty ring when a directory fails. #8 is blocked, not merely expensive: without a todo id or any history endpoint there is nothing to anchor an inline marker to. It stays on this page as a documented dead end so it is not re-proposed.

Not decided here: whether the ring is a button. Making it open the inspector tab is one line on desktop and a sheet on mobile, but it turns an ambient indicator into a control and needs its own data-testid and focus treatment. Proposed as a follow-up, not part of the first change.
