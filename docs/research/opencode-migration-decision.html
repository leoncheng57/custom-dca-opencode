1Verdict

Adopt OpenChamber upstream, pointed at your existing opencode serve. Do not fork it, and do not build a UI from scratch. But solve isolation and run-recovery first — those are the real migration blockers, not the UI.

  1. OpenChamber (openchamber/openchamber, 9.0k ★, 161 contributors, MIT, weekly releases) is React + Vite + Tailwind + Zustand over a plain Express BFF talking to @opencode-ai/sdk — structurally the same app you already maintain. It ships 8 of your 12 surfaces with none missing outright, and attaches to an external server via OPENCODE_HOST.
  2. The migration is viable: one server hosts all 32 of your projects (verified live), work continues when every client disconnects, and the API is richer than agent-canvas in most places.
  3. But two OpenHands properties have no equivalent and are load-bearing: R1 the agent no longer runs in a container — it runs as your user, and R2 there is no auto-resume, so a reboot mid-turn silently kills the run forever. Both need deliberate answers before this becomes your daily driver.
  4. Your OpenHands UI's real value was never the commodity panels — it was ntfy notifications, GitLab MR/pipelines, the command audit trail, and MCP/LSP latency probes. Nobody in the ecosystem has those four. They are yours to keep, in any path.

7OpenChamber in detail

Why it fits you specifically

React + Vite + Tailwind + Zustand in packages/ui; plain Express BFF in packages/web/server/lib/*, one folder per feature, colocated *.test.js, per-module DOCUMENTATION.md. Same shape as your server/openhands/*.ts + client/ds + vitest layout.

It attaches to your server

OPENCODE_HOST=http://100.78.52.59:4096 → probeExternalOpenCode() → "skip-start mode". External servers are treated as not-owned. Matches your one-stack-per-machine constraint: one OpenCode server, multiple BFFs.

Settings UI to copy wholesale

~20 sections on a shared SettingsPageLayout/SettingsSection primitive set: agents (+ real permissions editor), providers + OAuth, MCP full CRUD with OAuth authorize and paste-to-import, skills catalog, plugins, commands, git identities, notifications with per-event templates, tunnels, passkeys. Includes .agents/skills/settings-ui-patterns/SKILL.md.

8Where cmux + plugins still win

Server plugins REQUIRED

Notifications when no UI is open can only come from a server-side plugin. ntfy-notify.js works unchanged against opencode serve. Non-negotiable in every path — and doubly so given a parked permission prompt can stall a run forever (R8).

cmux Dock CHEAP

.cmux/dock.json hosting opencode mcp list, glab, lazygit, cmux feed tui is zero code for read-only monitoring — the cheapest MR/CI and MCP-health panes while the UI question settles.

cmux sidebar LIMITED

Ambient status only. It can natively see PRs, branch/dirty, unread, progress. It cannot do settings: no @State, no Toggle/TextField/Slider, no custom data source.

10Migration risk register

R1 CRITICAL  No container isolation

OpenHands ran the agent inside agent-canvas. OpenCode runs tools in-process as your UID. Binary string counts: seatbelt/sandbox-exec = 0, bwrap = 0, landlock = 0; every docker/container hit is syntax-highlighting grammar or MCP transport config, never an exec path. "Sandbox" in OpenCode means git worktree — Project.sandboxes is a list of directory strings.

Blast radius: a prompt injection can now read ~/.ssh, or exfiltrate ~/.local/share/opencode/auth.json (all provider keys) and mcp-auth.json (7.9 KB of live OAuth tokens). One server touching 32 project directories means one compromise reaches all 32.

Mitigation: run opencode serve inside your own container/VM, or as a dedicated low-privilege user with a restricted $HOME. Then layer permissions. Accept that permissions are advisory (in-process), not a boundary.

R2 CRITICAL  No auto-resume after restart

"Running" is process-local, never persisted. The session table has no status column; SessionStatus is an in-memory union; /api/session/active is documented as "owned by this OpenCode process." A durable input queue exists (session_input) but is empty on this install, gated behind OPENCODE_EXPERIMENTAL_EVENT_SYSTEM, and has no boot-time recovery sweep.

Impact: reboot mid-turn → the partial assistant message is in SQLite, the run is dead, nothing restarts it, and nothing tells you. Your autoResume.ts has no counterpart.

Resolution (Aug 21): ACCEPTED, detection-only. No recovery sweep — auto-re-prompting risks replaying destructive work. Instead, on session open the UI flags any session that is absent from GET /session/status whose last message is an assistant turn without time.completed, and offers a manual Resume that prefills the composer. See build plan Phase 2.
