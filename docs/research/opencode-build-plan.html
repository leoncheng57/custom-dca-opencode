—Overview

The port is not a rewrite. Every transcript row component consumes a neutral TranscriptEvent and touches zero raw agent-server fields, so the OpenHands coupling is concentrated in one function in one file (~363 lines of client/lib/events.ts). Everything else is a thin proxy swap, untouched code, or — after descoping — deliberately archived.

0Foundation

P0Foundation — the only gate
~half day

Goal: replace the container's two real jobs (execution guardrails, credential separation) with explicit host-side equivalents, and lock the API contract.

Replace the container boundary

  • Permission policy — the guardrail. bash defaults to allow; precedence is last-match-wins. Honest framing: 13 opencode TUI processes (some --auto) already ran host-side during research — this makes an existing posture deliberate, it does not add risk
  • Git identity: resolved — agents use your local git tools/credentials as-is. The bot-identity shell.env plugin is dropped; the OPENHANDS_GITHUB_TOKEN/OPENHANDS_GIT_TOKEN pair retires with the container
"permission": {
  "bash": { "*": "ask", "git *": "allow",
            "npm *": "allow", "rm -rf *": "deny" },
  "read": { "*": "allow", "~/.ssh/**": "deny",
            "~/.aws/**": "deny" },
  "external_directory":
          { "*": "ask",
            "~/Documents/Projects/**": "allow" }
}

Contract + ops

  • Pin the server binary; generate the client from the live GET /doc (162 paths) — not the docs site, not GitHub @dev, not dist/gen/ (use dist/v2/gen/ types)
  • launchd unit: pin --port (defaults to random 0), set HOME, NO_PROXY=localhost,127.0.0.1, OPENCODE_DISABLE_AUTOUPDATE, OPENCODE_SERVER_PASSWORD
  • Hygiene: 30.4 GB opencode.db (23.7 GB = event table) · 117 MB unrotated log · 4 plaintext tokens → {env:}

Docker teardown

  • No compose, no images, no volumes. Fixed-port constraint from AGENTS.md (8010/3210, one worktree runs the stack) evaporates — every worktree can run its own BFF against the shared daemon
Done when: a supervised opencode serve survives reboot on a pinned port with a written permission policy, the fresh public repo is scaffolded (ds/, vitest, CI, @shots copied over), and typecheck passes against a client generated from that server's /doc.

2Session lifecycle + interrupted detection

P2Session lifecycle
~2–3.5 days

Goal: create, run, stream, steer, stop — plus surface interrupted runs so R2 (accepted) is at least visible. End of this phase = usable agent IDE.

Endpoints

  • GET /session?directory=&roots=true&limit=
  • POST /session?directory= with {agent, model, permission}
  • POST /session/{id}/prompt_async — 204, non-blocking
  • POST /session/{id}/abort · DELETE /session/{id}
  • GET /session/status · GET /global/event SSE

Watch out

  • POST /session/{id}/message blocks the whole turn — never from the UI path
  • GET /event is directory-scoped; use /global/event, demux on payload.directory
  • No replay cursor on classic SSE — refetch on reconnect
  • Tolerate unknown event types (server.heartbeat every 10s is absent from the typed union)

Interrupted-run detection R2 · detect-only

  • On session open (not list-load — the messages are already fetched there; list-level would cost N requests):
interrupted =
    id NOT in GET /session/status   // not live anywhere
 && last msg is AssistantMessage
 && last msg .time.completed == null
  • Two states: last msg assistant+incomplete → "Run did not finish"; last msg user with no reply → "Never answered"
  • Neutral wording — a user abort has the identical signature; describe, don't diagnose
  • Resume button prefills the composer (decided) — no auto-send, so a run that already wrote files can't be replayed by a misclick
  • No background sweep, no auto-recovery, no state store — by explicit decision
Done when: create → stream → steer mid-run → abort → resume works across two synced tabs; killing the server mid-turn and reopening the session shows the interrupted banner with a working Resume.

—One-shot execution — background subagents on Opus 5

The plan above is estimated at human pace (~2.5 weeks). The same work, executed by parallel opencode sessions on anthropic/claude-opus-5 with you reviewing at the acceptance gates, compresses to ~2–4 days of wall clock. This document is written to be the execution harness: every phase card is a self-contained worker prompt with its own goal, endpoints, deletions, traps, and a testable "done when".

Setup (once, part of Phase 0)

StepHowNote
Pin the model"model": "anthropic/claude-opus-5" in the new repo's opencode.jsonAlready proven on this machine — the research subagent sessions ran on it (visible in live GET /session payloads)
Enable background subagentsOPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=1 in the launchd unit's envCurrently off: GET /experimental/capabilities → {"backgroundSubagents": false}. Verify it flips to true after restart
Raise nesting if needed"subagent_depth": 2Lets a coordinating session's subagents spawn their own explore helpers

Two parallelization primitives — use both

In-session task subagentsParallel worker sessions in worktrees
WhatOne coordinating session fans out subagents; POST /experimental/session/{id}/background detaches blocking ones so the parent keeps workingIndependent sessions, each created with ?directory=<worktree>, each on its own branch — the manager-children cmux skill pattern

Wave plan

WAVE 0  (serial · HUMAN + one session · ~2h)
  P0 foundation — permission policy is human-reviewed before any agent runs
  scaffold fresh public repo (agent does the copying: ds/, vitest, CI, @shots)

WAVE 1  (serial · ONE focused session · ~half day)
  P1 the seam — single critical path; adapter output types are FROZEN at merge
  every later worker imports these types read-only

WAVE 2  (parallel · 4 worker sessions in 4 worktrees)
  worker A: P2 lifecycle + interrupted detection
  worker B: P3 free ports (MR panel, commands, notify UI)
  worker C: P4 files + changes (+ local git log)
  worker D: P5 task list + status bar + tools&health
  B/C/D depend only on frozen P1 types; A also owns the SSE store

WAVE 3  (parallel · 3 worker sessions)
  worker E: P6 settings    worker F: P7 resilience    worker G: P8 worktrees

WAVE 4  (serial · one session + human)
  integration pass: merge in order A→D→C→B→E→F→G, run e2e, fix seams
  P9 cutover checklist

Worker prompt recipe

  • Each worker gets: its phase card from this document verbatim (goal, endpoints, deletions, traps, done-when) + the Part→TranscriptEvent table + the stub-routes list + the frozen adapter type file
  • Contract per worker: "done" = npm run typecheck && npm test pass and your phase's done-when is demonstrated — the acceptance criteria in this doc are the review gates, verbatim
  • Workers open draft PRs; you review at wave boundaries, not mid-flight
  • Rule: no worker touches another phase's files; shared types change only via a wave-1 amendment PR that everyone rebases on
Honest limits of "one shot". A single unattended prompt for all 10 phases will compound errors at the seam — if P1's mapping is subtly wrong, four parallel workers build on the mistake. The realistic fast path is one wave per sitting with a 15-minute review between waves (~5 sittings total). Also budget for it: research subagent sessions on Opus 5 ran $0.7–1.3 each; build waves with 4 concurrent workers will run substantially more — expect tens of dollars per wave. Watch spend via each session's cost field, which your own Phase 5 status bar will display.
Why this plan is unusually automatable: the riskiest unknown (P1) is deliberately first and small; every phase has a machine-checkable exit; the traps that would burn an agent (blocking /message, directory-scoped /event, stub routes, last-match-wins permissions, missing Todo.id) are enumerated; and workers can't collide because phase boundaries were drawn along file boundaries.
